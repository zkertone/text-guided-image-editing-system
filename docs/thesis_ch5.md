# 第5章 系统实现

## 5.1 开发环境与运行环境

为完成本课题所设计的文字驱动图像编辑系统，本文采用 Python 作为主要开发语言，并基于 PyTorch 与 Hugging Face Diffusers 框架完成预训练模型的调用与推理实现。在开发环境配置方面，系统可通过 Anaconda 或 Miniconda 创建独立虚拟环境，以便统一管理 PyTorch、Diffusers、Transformers、Gradio 等依赖库，降低环境冲突对项目运行的影响。

在模型与推理框架方面，系统主要使用 Hugging Face Diffusers 提供的预训练扩散模型管线。其中，整体编辑功能基于 InstructPix2Pix 管线实现，局部编辑功能基于 Stable Diffusion Inpainting 管线实现，结构保持编辑功能基于 Canny ControlNet 管线实现。系统推理过程依赖 PyTorch 完成张量计算，并根据运行设备自动选择 CPU 或 GPU 环境。在具备 CUDA 支持的环境下，系统优先使用 GPU 进行推理，以提高生成速度和使用体验。

在交互界面方面，系统采用 Gradio 构建浏览器端可视化操作界面。用户无需编写额外代码，即可通过网页完成图像上传、Prompt 输入、Mask 指定、参数设置和结果查看等操作。这种方式较适合本课题原型系统的快速搭建，也便于后续实验演示和论文答辩展示。

在运行环境方面，考虑到扩散模型推理对显存和计算资源有一定要求，本系统主要采用 GitHub 与 Google Colab 相结合的方式进行开发与测试。项目代码保存在 GitHub 仓库中，用于版本管理与文件同步；具体运行与实验测试则可在 Google Colab 的 GPU 环境中完成。该方式能够在不依赖本地高性能显卡的条件下完成系统验证，较符合本科毕业设计的实际条件。

此外，为便于实验结果管理，系统在运行过程中会自动保存输入图像、输出图像和控制图像，并将实验参数、提示词和结果路径记录到 CSV 文件中。通过这种方式，系统不仅完成图像编辑功能实现，也为后续实验分析和论文撰写提供了必要的数据支持。

## 5.2 系统整体实现说明

本系统的实现目标并非从零训练新的图像生成模型，而是在预训练模型基础上完成一个面向实际使用的文字驱动图像编辑原型系统。因此，在系统实现过程中，本文重点关注的是不同编辑模式的调用流程组织、图像输入输出处理、用户交互方式设计以及实验记录机制的建立。

从整体实现过程看，系统首先在启动阶段完成预训练模型管线的加载。根据不同编辑任务的需求，系统分别初始化整体编辑、局部编辑和结构保持编辑所对应的推理管线，并自动检测当前运行设备，设置相应的数据类型与推理参数。在此基础上，系统创建统一的图像编辑器对象，将图像预处理、Mask 处理、控制图生成、结果保存和日志记录等操作封装在同一业务逻辑模块中，从而为不同模式下的图像编辑提供统一的调用入口。

在用户使用过程中，系统通过 Gradio 构建可视化界面，将编辑模式选择、原图上传、Mask 输入、提示词输入和参数调节等功能整合在统一页面中。对于整体编辑模式，系统直接接收原始图像和文本指令，并调用 InstructPix2Pix 管线完成整图编辑；对于局部编辑模式，系统会额外接收用户指定的编辑区域，并结合 Inpainting 管线在局部范围内生成结果；对于结构保持编辑模式，系统则先提取输入图像的 Canny 边缘图，再将其作为 ControlNet 的条件输入参与推理，以增强生成结果对原始结构轮廓的保持能力。

在结果处理方面，系统在完成每次推理后，会自动保存输入图像、输出图像以及必要的控制图像，并在界面中展示当前实验的摘要信息。与此同时，系统将本次实验涉及的提示词、推理步数、引导强度、图像尺寸、输入路径和输出路径等关键信息追加记录到实验日志文件中。这样既有助于后续对不同实验结果进行对比分析，也便于论文撰写时对案例来源、参数设置和结果路径进行整理。

总体来看，本系统的实现过程体现出较强的工程集成特点。其核心不在于修改底层扩散模型结构，而在于围绕预训练模型完成多种编辑模式的组织与实现，并通过界面、日志和文件管理等机制增强系统的可用性与可记录性。对于本科毕业设计而言，这种实现方式既符合课题要求，也能够较真实地反映系统从功能设计到原型落地的完整过程。

## 5.3 整体编辑功能实现

整体编辑功能是本系统最基础的图像编辑功能，其主要目标是在不额外指定局部区域的情况下，根据用户输入的文本指令对整幅图像进行语义驱动修改。该功能基于预训练 InstructPix2Pix 管线实现，适用于整体色调变化、背景调整以及风格变换等场景。

在实现流程上，系统首先接收用户上传的原始图像，并读取输入的英文编辑指令及相关推理参数，如推理步数、图像引导强度和文本引导强度等。为保证后续模型推理的稳定性，系统会先对输入图像进行统一预处理，包括颜色空间转换、尺寸规范化以及数据格式调整等操作。完成预处理后，系统将图像与文本提示词共同送入 InstructPix2Pix 管线，由模型根据输入语义生成编辑后的图像结果。

从工程实现角度看，整体编辑功能的关键在于将预训练模型调用过程封装为可重复使用的统一接口。系统在图像编辑模块中对整体编辑逻辑进行了独立组织，使得界面层只需传入原图、提示词和参数，即可获得对应结果，而无需直接处理模型底层调用细节。这种实现方式一方面简化了系统模块之间的耦合关系，另一方面也便于后续与其他编辑模式统一管理。

整体编辑功能在使用方式上较为直接，适合作为系统最基本的文字驱动图像编辑能力进行展示。从当前实验结果看，该模式在颜色变化、整体风格调整等任务上能够得到较明显的编辑效果。但由于编辑对象是整幅图像，在部分情况下模型会对非目标区域产生连带修改，因此该模式更适合用于整体视觉变化较强、局部精确控制要求相对较低的场景。

在每次整体编辑完成后，系统会自动保存输入图像和输出图像，并在实验摘要中记录当前所用模型、运行设备、提示词和主要参数。同时，本次实验的相关信息会被追加写入 CSV 日志文件，以支持后续实验对比与案例整理。

## 5.4 局部编辑功能实现

为提高图像编辑的针对性与可控性，系统在整体编辑功能基础上进一步实现了局部编辑功能。该功能基于 Stable Diffusion Inpainting 管线完成，其核心思想是在用户指定的局部区域内进行内容生成或修改，而未被选中的区域尽量保持不变。相比整体编辑，局部编辑更适用于目标明确的局部替换、颜色调整和属性修改任务。

在具体实现中，局部编辑功能需要同时接收原始图像、局部区域信息和文本提示词。其中，局部区域信息以 Mask 的形式给出，系统当前支持两种方式获取 Mask：一种是由用户直接上传黑白 Mask 图，另一种是由用户在界面中在线绘制 Mask。无论采用哪种方式，系统最终都会将区域信息统一转换为标准黑白 Mask 图，其中需要编辑的区域对应白色部分，保持不变的区域对应黑色部分。通过这种方式，可以将不同来源的用户输入统一组织为 Inpainting 管线所需的数据格式。

在推理过程中，系统首先对原始图像和 Mask 图进行预处理，使其在尺寸、通道格式和数据类型上满足模型输入要求。随后，将原始图像、Mask 图和文本提示词共同送入 Inpainting 管线，由模型在指定区域内执行图像补全与编辑操作，并生成最终结果。由于系统对 Mask 获取和处理过程进行了统一封装，因此用户只需在界面中完成区域指定，而无需关心底层数据转换过程。

从实现效果来看，局部编辑功能相较于整体编辑具有更高的操作针对性，能够在一定程度上减少非目标区域的无关变化。例如，在局部灯光颜色调整等任务中，通过在线绘制 Mask 可以更准确地约束编辑范围，使系统将修改集中在用户指定区域内。但与此同时，当目标区域纹理较为复杂时，如头发、细小边缘或高频纹理区域，局部编辑结果仍可能出现边界不自然或语义修改不够稳定等问题。这也说明该功能在工程上已经具备实用性，但结果质量仍受预训练模型本身能力限制。

在实验记录方面，系统在局部编辑完成后，同样会自动保存输入图像、Mask 图和输出图像，并在实验摘要中展示当前 Mask 来源、提示词和主要推理参数。相关结果路径和参数信息也会同步写入实验日志文件中，以便后续分析不同区域指定方式对编辑结果的影响。

## 5.5 结构保持编辑功能实现

在整体编辑和局部编辑之外，为进一步增强编辑结果对原始图像结构信息的保持能力，系统实现了基于 Canny ControlNet 的结构保持编辑功能。该功能的基本思路是先从输入图像中提取边缘结构信息，再将其作为条件输入与文本提示词共同送入 ControlNet 管线，从而在生成过程中对图像主要轮廓和结构关系进行约束。

在具体实现流程上，系统首先接收用户上传的原始图像和文本提示词，然后对输入图像执行 Canny 边缘检测，得到对应的边缘控制图。该控制图能够保留原图中的主要轮廓和结构信息，并作为后续推理过程中的附加条件。完成边缘图提取后，系统将原图、控制图和提示词共同输入到基于 Stable Diffusion 的 ControlNet 管线中，生成满足文本语义且受结构约束的结果图像。

从工程实现角度看，该功能的关键在于将控制图生成过程与模型推理解耦。系统在图像编辑模块中先独立完成 Canny 边缘图生成，再统一组织为 ControlNet 管线输入格式。这样不仅使代码结构更加清晰，也便于后续对边缘提取方式或控制条件进行进一步扩展。与此同时，系统还将生成的 Canny 控制图返回到界面中展示，并保存到本地目录中，便于用户观察结构约束信息与最终结果之间的关系。

与整体编辑相比，结构保持编辑模式更强调对原图空间轮廓的保留，因此更适合用于风格化变化或在保持主要结构前提下进行视觉改写。例如，在以“cyberpunk light”为提示词进行实验时，系统能够在保留输入场景主要轮廓的基础上生成具有明显风格变化的结果。需要指出的是，该模式更适合结构层面的约束与风格转换，在处理精细属性微调任务时，其表现未必优于局部编辑方式。因此，该功能更适合作为一种面向结构保持需求的扩展编辑模式，而非对所有编辑任务都具有优势的通用方案。

在功能实现完成后，系统会自动保存输入图像、Canny 控制图和输出图像，并在实验摘要中展示当前模型类型、控制方式、提示词和相关参数。与此同时，本次实验的结果路径和参数信息也会写入 CSV 实验日志，为后续结构保持案例分析和论文实验章节提供材料支持。

## 5.6 交互界面实现

为提高系统的可用性与演示性，本文采用 Gradio 构建文字驱动图像编辑系统的可视化交互界面。相较于仅通过脚本或命令行调用模型，Gradio 界面能够将图像上传、参数设置、模式选择和结果展示等操作集中在统一页面中，更适合本课题原型系统的功能验证、实验操作和论文答辩展示。

在界面布局设计上，系统围绕三种编辑模式组织交互流程，主要包括编辑模式选择区、输入图像上传区、Mask 指定区、文本提示词输入区、参数设置区、结果展示区以及实验信息展示区等部分。用户进入界面后，可首先选择整体编辑、局部编辑或结构保持编辑模式，随后根据不同模式上传原始图像，并输入对应的英文编辑指令。对于需要参数控制的场景，界面还提供推理步数、图像引导强度和文本引导强度等可调参数，以满足不同实验条件下的测试需求。

针对局部编辑模式，界面额外提供了两种 Mask 指定方式，即上传黑白 Mask 图和在线绘制 Mask。系统会根据用户的选择动态显示相应控件，从而减少无关输入项对操作流程的干扰。对于结构保持编辑模式，界面在结果展示区域中增加了 Canny 控制图显示功能，以便用户直观观察输入结构条件与输出结果之间的关系。通过这种按模式动态调整控件显示状态的设计，系统能够在保持界面完整性的同时，提高不同功能场景下的操作清晰度。

在结果展示方面，界面不仅显示最终编辑图像，还会在必要时展示控制图，并以文本形式输出实验信息摘要。摘要内容包括当前编辑模式、所使用模型、运行设备、提示词、推理参数以及输入输出文件保存路径等信息。这一设计既便于用户及时了解当前实验设置，也为后续结果整理与案例分析提供了直接参考。

总体来看，基于 Gradio 的交互界面实现，使本系统从单纯的模型调用程序进一步发展为具有可视化操作能力的图像编辑原型系统。该界面能够较好地满足实验操作、案例演示和答辩展示等实际需求，是本课题工程实现的重要组成部分。

## 5.7 结果保存与实验日志实现

为了提高实验过程的可追溯性与结果管理的规范性，系统在图像编辑功能实现的基础上，进一步设计并实现了结果保存与实验日志记录机制。相较于仅返回一次性的编辑结果，这一机制能够对实验输入、输出及参数信息进行留档，为后续实验对比、案例分析和论文写作提供支持。

在结果保存方面，系统会在每次推理完成后自动保存输入图像和输出图像。对于结构保持编辑模式，还会额外保存生成过程中使用的 Canny 控制图。保存文件按照预设目录分类存放于 `data` 目录下，以便后续按照实验类型或时间顺序进行检索与整理。通过保留输入图像、控制图像和输出图像之间的对应关系，可以更清晰地分析不同输入条件对生成结果的影响。

在实验信息展示方面，系统会根据本次运行结果生成实验摘要，并直接在界面中输出。摘要内容主要包括编辑模式、模型名称、运行设备、提示词、推理步数、引导强度、图像尺寸以及输入输出路径等信息。与单纯保存图片相比，这种摘要方式能够同时保留实验配置与结果位置，为后续论文中案例参数说明提供便利。

在日志记录方面，系统采用 CSV 文件作为实验日志保存格式。在每次图像编辑完成后，程序会将当前实验的时间戳、提示词、推理步数、图像引导强度、文本引导强度、图像尺寸、输入路径和输出路径等关键信息追加写入实验日志中。之所以采用 CSV 格式，主要是因为其结构清晰、便于追加写入，同时也便于后续借助电子表格工具或脚本进行统计分析。对于本科毕业设计而言，这种轻量化的记录方式能够在不增加系统复杂度的前提下，较好地满足实验留档与结果整理需求。

此外，系统还对版本记录和案例整理进行了配套设计。通过版本说明文档记录不同阶段的功能变化情况，通过案例目录与案例索引文件对典型实验结果进行分类保存，从而使结果保存机制不仅服务于系统运行本身，也服务于论文写作和答辩展示材料的整理。总体而言，结果保存与实验日志功能的实现，使系统具备了基本的实验管理能力，也进一步体现了本课题工程实现型毕业设计的特点。

## 5.8 基于 GitHub 与 Colab 的运行测试流程

考虑到扩散模型推理对计算资源具有一定要求，而本科毕业设计阶段本地硬件条件可能存在限制，本文在系统运行与测试过程中采用 GitHub 与 Google Colab 相结合的方式进行实现。该流程既满足了项目代码管理的需求，也为系统原型在云端 GPU 环境下的运行和实验提供了便利。

在项目管理方面，系统代码统一保存在 GitHub 仓库中。通过 GitHub，可以对项目源代码、文档说明和版本迭代记录进行集中管理，并在功能更新后及时同步到远程仓库。这种方式有助于保持代码版本的一致性，也便于在不同设备或不同运行环境中获取最新项目内容。对于本课题而言，GitHub 主要承担代码托管、版本记录和项目同步的作用。

在运行测试方面，系统主要通过 Google Colab 提供的云端环境进行启动与验证。用户可在 Colab 中配置 Python 运行环境，安装 `requirements.txt` 中所需依赖，并从 GitHub 拉取项目代码。完成环境配置后，即可在 Colab 提供的 GPU 运行时中启动 Gradio 界面并执行图像编辑实验。相较于仅依赖本地设备运行，这种方式能够在一定程度上缓解显卡性能和显存容量不足的问题，提高系统原型验证的可行性。

在具体流程上，首先需要从 GitHub 获取项目最新代码，并在 Colab 中完成运行环境配置。随后，根据项目依赖安装 PyTorch、Diffusers、Transformers、Gradio 等所需库，并加载对应预训练模型。系统运行后，用户可通过 Gradio 页面执行整体编辑、局部编辑和结构保持编辑等实验操作。实验过程中生成的输入输出图像、控制图和日志记录可按项目设计保存到对应目录中，作为后续案例整理和论文分析的依据。
